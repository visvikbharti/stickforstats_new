## 3. `5c87d00` was itself wrong, and is now fixed (`b8f4198`)

`_fit_is_exact` compared `max|residual|` to `max|y|` — the **magnitude** of y — while both
diagnostics ask about its **variation**. It was scale-invariant but **not shift-invariant**.

Measured on `main + e442b84 + 5c87d00`, growing variance (n=60, sd 0.002→0.045, a 23.5× fan),
**R² identical to ten decimal places at every offset**:

```
offset 0 … 1e11  -> confidence 0.306, can_proceed False, homoscedasticity CRITICAL
offset 1e12,1e13 -> confidence 0.444, can_proceed TRUE,  homoscedasticity ABSENT
```

And on genuinely quadratic data (true R² = 0.9999996) at offset 1e12, linearity returned a PASS
reading *"reproduces y exactly to within floating-point precision (R² = 1)"* — **an affirmative
claim about the data that is false**, which is worse than the accusation it replaced. Realistic
trigger: epoch-**nanosecond** timestamps. A single extreme leverage point does it too.

### The constant's justification was wrong

The file recorded worst-case dust at **21.9 ULPs**. Re-measured over n ∈ 10…20,000 and five
x-distributions, the worst dust for an exactly linear y is **696.6 ULPs** — the old sweep never
reached the ill-conditioned corner. So `1000` sat **1.4× above worst-case dust, not 46×**, and
the signal being silenced sits at ~375 ULPs, *inside* the claimed margin.

**The two populations overlap on that statistic, and on every alternative I tried**
(`max|r|/ptp`, ULPs of `ptp`, `1−R²`). No single threshold separates them. So the fix is a
**second, shift-invariant condition**, not a tuned constant:

- `_residual_information_floor(y) = _EXACT_FIT_ULPS · eps · max|y|` — the representation floor.
- `_variation_is_resolvable(y)` — is that floor negligible against `np.ptp(y)`? No offset can
  change `ptp`, which is the whole point.

Measured separation: legitimate exact fits reach `floor/ptp = 6.97e-12` at worst (80 samples);
the wrongly-silenced cases sit at `1.64e-05` (epoch-ns) and `9.41e-04` (growing variance).
`1e-9` is 143× above the former and 16,000× below the latter. `_EXACT_FIT_ULPS` 1000 → **5000**.

**Nesting is load-bearing and my first attempt got it wrong.** Applied *before* the exactness
test, the gate also swallowed data with real signal left to evaluate — the same growing-variance
case at offset 1e9, whose noise is four orders of magnitude above float64 spacing, went from
correctly CRITICAL to "not evaluated". The gate belongs **inside** the exact-fit branch, and a
test pins that case.

Where the answer is genuinely indeterminate we now say so and say what to do: both validators
report NOT EVALUATED with an explanation that **centring y changes no regression result and
makes the assumption checkable**.

### Two more instances of the `e442b84` defect class, both live in v1.2.0

- `guardian_core.py:943` read `result["severity"]`, `["message"]`, `["recommendation"]`
  unguarded → a validator reporting a violation without one raised `KeyError` out of `check()`
  and became a non-200. Now degrades the report instead of failing the request.
- scipy returns `nan` for skew/kurtosis of a **constant column**; `nan` is not JSON, and DRF's
  renderer turned the whole check into a 500. Executed: a constant `y` 500'd
  `/api/guardian/check/` on v1.2.0 *and* on this branch. Now 200 with those fields **null** —
  null, not 0.0, because the shape of a distribution with no spread is undefined and
  "skewness 0" would be a fabricated number.

### 🚨 Scope, stated plainly — this does NOT reach CSV or float32 users

Measured before → after, 300 perfect lines each:

| storage | homo % | lin % |
|---|---|---|
| float64 in memory | 71.3 → **0.0** | 53.0 → **0.0** |
| **float32 array** | 88.3 → **88.3** | 40.3 → **40.3** |
| **CSV `%.6g`** | 65.7 → **65.7** | 53.7 → **53.7** |
| CSV `%.10g` / `%.12g` | ~61 → ~61 | ~57 → ~57 |
| CSV `%.15g` / `%.17g` | 58.3 → **0.0** | 56.3 → **0.0** |

The representation floor is below every storage format short of a full float64 round-trip. **A
user uploading an ordinary CSV of an exact line is still falsely accused.** That is a separate,
unfixed defect. Deciding whether quantised storage is in scope is the next design question.

### New, and not previously known

- **Row ORDER drives the linearity rate, not the data.** `_runs_test` runs Wald–Wolfowitz on
  residuals in submission order. Same x-distribution, same perfect line: x **sorted → 73.0%**
  flagged; the identical x left **unsorted → 2.0%**. Any time, dose, concentration or index
  predictor is submitted sorted, so the affected population skews toward real datasets.
- **Mutation testing of `5c87d00` in its landing context: 26 applied, 17 caught, 9 survived** —
  including `max|y| → np.ptp(y)`, which is *the very design choice that caused the shift bug*,
  changing behaviour with zero test response. Root cause: the guard's real decision boundary is
  479.5–1876 ULPs and the module's fixtures sat at 2.91, 5.97 and 1.15e10 — **no fixture within
  nine orders of magnitude of the boundary.**

## 6. Process notes from this session

- **`git worktree add <path> main` checks out the real branch.** Cherry-picking in that worktree
  moved local `main`. Caught, reset to `51f58d7`, verified against `origin/main`, nothing pushed.
  Use `git worktree add --detach <path> <sha>` for throwaway experiments.
- **`git checkout -- <file>` restores to HEAD and wipes uncommitted work.** A mutation-testing
  loop that used it to revert each mutation destroyed an entire uncommitted fix. Commit first,
  then mutate — the loop is only safe once HEAD *is* the thing you want restored.
- **A test that asserts only at the observed worst case pins nothing.** Reverting
  `_EXACT_FIT_ULPS` to the old 1000 survived the first sweep because the lower bracket asserted
  exactness at 696.6 ULPs, which 1000 clears. Since the previous measurement of that same
  quantity was 32× low, the assertion now requires **twice** the observed worst case — it pins
  the design rule rather than a magic number.
