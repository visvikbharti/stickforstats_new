### Two things about the gates that you must know

**(a) `pytest tests/` shows 21 failures. They are pre-existing and CI cannot see them.**
They live in `tests/test_power_analysis_validation.py`, which uses plain classes rather than
`unittest.TestCase` — so Django's test runner, **which is what CI runs**, never collects the file.
They exercise `core/power_analysis.py`, a *second, legacy power engine* that is badly broken
(`TypeError`, "not yet implemented", missing methods). Verified: they fail identically on a clean
checkout of `main` with all local work stashed. Verified: `core/api_views.py` is the only importer
of that engine, and **no `urls.py` routes to it** — so it is dead code, not a live endpoint.

**(b) CI's eslint does not lint a single `.jsx` file.**
CI runs `npx eslint src/` which, in eslintrc mode, expands a directory to `.js` only (plus whatever
`overrides[].files` globs imply — and `eslint-config-react-app`'s only such glob is `**/*.ts?(x)`).
Executed: CI's exact command visits **293 files (267 `.js`, 20 `.tsx`, 6 `.ts`) and ZERO of the
repo's 469 `.jsx` files**, reports 0/0, and exits 0. So `--max-warnings 0` passes vacuously.

Adding `--ext .js,.jsx,.ts,.tsx` makes it visit 762 files and surface **46 errors and 1030
warnings — every one of them in a `.jsx` file.** Among them `no-use-before-define` fires 7 times:
that is the exact temporal-dead-zone class that caused the recent P0 crashes (chi-square screen,
ML train, CI plot). **The rule was enabled and would have caught them. CI simply never looked.**

## 3. Deployment

**Mechanism** (from `DEPLOYMENT_RUNBOOK.md`, confirmed against `ci.yml` and `docker-compose.yml`):

1. CI on `main` pushes images to GHCR: `ghcr.io/visvikbharti/stickforstats_new/{backend,frontend}`,
   tagged `:latest` **and** `:<full-git-sha>`.
2. **CI does not deploy.** The `staging-deploy` job only echoes. Deployment is a manual operator step.
3. On the host: pull the `:<sha>` images, **retag them to `stickforstats/{backend,frontend}:1.0.0`**,
   then `docker compose up -d --no-build`.

Compose has both `build:` and `image:` keys, so a plain `docker compose up` **builds locally and
never pulls**. `--no-build` after retagging is what makes it use the published images.

### ⚠ The host is armed with a stale build

Verified by inspection of the host on 2026-07-14:

    stickforstats/frontend:1.0.0  -> eec504cb3315   <- these are the b252163 images,
    stickforstats/backend:1.0.0   -> d6071dded452      NOT the current main

Running containers hold their image by ID, so live is *currently* unaffected — but **any
`docker compose up -d` for any reason would deploy `b252163`**, a mid-arc commit. Retag `:1.0.0` to
the intended SHA *before* bringing the stack up. Always.

**Rollback point** — tagged on the host, and it is what is running now:

    stickforstats/frontend:rollback-prev -> d34a01ea5bcd
    stickforstats/backend:rollback-prev  -> d4ad5640ffdc     (= 7a8dced)

### Deploy blocker, now fixed

`docker-build` has `needs: [backend-test, frontend-test]`, and `docker-push` needs `docker-build`.
So **one flaky frontend test blocked the image push entirely** — which is why no images existed for
recent commits and why the host still held `b252163`. The flake is fixed (see
`DEFECTS_AND_PATTERNS_2026-07-14.md`, §3): 4 consecutive full runs green.

Note also: **lint does not gate the deploy.** `docker-build`'s `needs:` lists only the two test jobs.
A red lint job does not stop the image push.

## 4. Configuration bugs found (not yet fixed)

Found by reading `docker-compose.yml` against `settings.py`. These are **not** blocking the deploy —
they are pre-existing — but they matter:

- **The reproducibility receipt is silently unsigned in production.** `RECEIPT_RSA_PRIVATE_KEY_B64`
  and `RECEIPT_RSA_KEY_ID` appear **nowhere in `.env.example`**, and are not fail-closed. An operator
  following the runbook's `cp .env.example .env` gets no receipt key, so the backend generates an
  **ephemeral** one. The backend runs gunicorn with `--workers 4` and no `--preload`, so *each worker
  generates a different RSA keypair while advertising the same key id*
  (`stickforstats-receipt-ephemeral`). Signature verification is therefore a coin flip. The receipt
  is supposed to be the product's moat.
- Those same vars are passed **only to the `backend` service** — `celery` and `celery-beat` run the
  same image and receive neither.
- **`JWT_SECRET` is dead config**: compose fail-closed *requires* it, `.env.example` defines it, and
  **no backend code reads it**. `auth_service` reads `JWT_SECRET_KEY`.
- If `DATABASE_URL` is unset the backend **silently falls back to SQLite**. Compose sets it, so the
  compose path is safe — but any bare `manage.py` invocation writes to `db.sqlite3`.
- If Redis is unreachable at import time, settings **silently falls back to LocMemCache** (per
  gunicorn worker) with only a stdout warning.
- `nginx/ssl/` and `nginx/sites-enabled/` are mounted by compose but **do not exist in the repo** —
  TLS material must already be on the host.
