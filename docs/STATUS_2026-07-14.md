### Two things about the gates that you must know

**(a) `pytest tests/` shows 21 failures. They are pre-existing and CI cannot see them.**
They live in `tests/test_power_analysis_validation.py`, which uses plain classes rather than
`unittest.TestCase` — so Django's test runner, **which is what CI runs**, never collects the file.
They exercise `core/power_analysis.py`, a *second, legacy power engine* that is badly broken
(`TypeError`, "not yet implemented", missing methods). Verified: they fail identically on a clean
checkout of `main` with all local work stashed. Verified: `core/api_views.py` is the only importer
of that engine, and **no `urls.py` routes to it** — so it is dead code, not a live endpoint.

**(b) CI's eslint did not lint a single `.jsx` file. Fixed 2026-07-14.**
CI ran `npx eslint src/` which, in eslintrc mode, expands a directory to `.js` only (plus whatever
`overrides[].files` globs imply — and `eslint-config-react-app`'s only such glob is `**/*.ts?(x)`).
Executed: that command visited **293 files (267 `.js`, 20 `.tsx`, 6 `.ts`) and ZERO of the repo's 469
`.jsx` files**, reported 0/0, and exited 0. `--max-warnings 0` was passing **vacuously**.

CI now runs `npm run lint` (`--ext .js,.jsx,.ts,.tsx`), which visits **764 files**, and lint is in
`docker-build`'s `needs:` so it actually gates the image push. `no-use-before-define` is now an
**error** (it was a warning), using react-app's own options — `variables: false` catches the
dangerous *same-scope* TDZ; `variables: true` would report 399 mostly-harmless outer-scope sites.

It found **7 real, unconditional `ReferenceError`s**, all now fixed and regression-tested:
a local `const isSignificant` shadowing the imported helper (3 files in
`MultiplicityCorrectionPanel/`); a `useEffect` **deps array** naming a `const` declared below it
(`ConversationHistory`, `SourcesExplorer`) — a deps array is an ordinary argument, evaluated eagerly
during render; and a JSX **value** const reading a handler defined 500 lines later
(`DairyPasteurizationCUSUM`).

**Honest scope:** all 7 live in components **no route currently renders** — none was a live crash.
But the identical pattern *did* crash the chi-square screen, ML train and CI plot on 2026-07-13
(`IntervalVisualization.render.test.jsx` documents that exact deps-array TDZ). **The rule was enabled
the whole time and would have caught every one of them. CI simply never looked.**

`--max-warnings 1064` is a **ratchet** — the current count, so the gate cannot get worse. The 45
testing-library errors in test files are downgraded to warnings (counted, not hidden). Burn them down
and lower the number.

## 3. Deployment

**Mechanism** (from `DEPLOYMENT_RUNBOOK.md`, confirmed against `ci.yml` and `docker-compose.yml`):

1. CI on `main` pushes images to GHCR: `ghcr.io/visvikbharti/stickforstats_new/{backend,frontend}`,
   tagged `:latest` **and** `:<full-git-sha>`.
2. **CI does not deploy.** The `staging-deploy` job only echoes. Deployment is a manual operator step.
3. On the host: pull the `:<sha>` images, **retag them to `stickforstats/{backend,frontend}:1.0.0`**,
   then `docker compose up -d --no-build`.

Compose has both `build:` and `image:` keys, so a plain `docker compose up` **builds locally and
never pulls**. `--no-build` after retagging is what makes it use the published images.

### ⚠ The host is armed with a stale build

Verified by inspection of the host on 2026-07-14:

    stickforstats/frontend:1.0.0  -> eec504cb3315   <- these are the b252163 images,
    stickforstats/backend:1.0.0   -> d6071dded452      NOT the current main

Running containers hold their image by ID, so live is *currently* unaffected — but **any
`docker compose up -d` for any reason would deploy `b252163`**, a mid-arc commit. Retag `:1.0.0` to
the intended SHA *before* bringing the stack up. Always.

**Rollback point** — tagged on the host, and it is what is running now:

    stickforstats/frontend:rollback-prev -> d34a01ea5bcd
    stickforstats/backend:rollback-prev  -> d4ad5640ffdc     (= 7a8dced)

### Deploy blocker, now fixed

`docker-build` has `needs: [backend-test, frontend-test]`, and `docker-push` needs `docker-build`.
So **one flaky frontend test blocked the image push entirely** — which is why no images existed for
recent commits and why the host still held `b252163`. The flake is fixed (see
`DEFECTS_AND_PATTERNS_2026-07-14.md`, §3): 4 consecutive full runs green.

Note also: **lint does not gate the deploy.** `docker-build`'s `needs:` lists only the two test jobs.
A red lint job does not stop the image push.

## 4. Configuration bugs

### ⚠ Correction: the receipt was NOT unsigned in production

An earlier version of this document said *"the reproducibility receipt is silently unsigned in
production."* **That was false.** I inferred it from `.env.example` and `docker-compose.yml` without
checking the host. Verified against the live host on 2026-07-14: `RECEIPT_RSA_PRIVATE_KEY_B64` **is**
set, and six JWKS calls (round-robining the 4 gunicorn workers) all return the **same** key,
`kid=stickforstats-receipt-prod-1`. **Production receipts are properly signed and verifiable.**

*A plausible inference is not a verification.* Same rule as the beta password in §5 — I applied it
there and failed to apply it here.

### What was actually wrong — fixed 2026-07-14

- `RECEIPT_RSA_*` was in **no `.env.example`** (0 occurrences), and **no command emitted the `_B64`
  form** the runbook asked for. An operator following `cp .env.example .env` provably could not end
  up with a key. Both fixed; `generate_receipt_keypair --env` now prints the exact lines, and a test
  round-trips its output back through the loader.
- With no key, the failure was **silent**: 4 workers minted 4 different keys **all advertising the
  same key id**, so the key-id check passed and only the crypto failed — a genuine receipt reported
  invalid, undiagnosable. Ephemeral key ids now carry the key's fingerprint, and signing is
  **fail-closed** when `DEBUG=False` (escape hatch `RECEIPT_ALLOW_EPHEMERAL_KEY=1`).
- The guard sits at **key-load time, not `AppConfig.ready()`**, deliberately: the image runs
  `manage.py collectstatic … 2>/dev/null || true` at build time with `DEBUG=False`, so raising during
  app startup would have been **swallowed by that `|| true`** and shipped an image with no static
  files. A safety fix that silently breaks production is the exact defect class this project keeps
  reproducing.
- **The downloadable bundle embedded the serving process's public key**, not the key that signed the
  receipt. Executed proof: after a routine key rotation, our own shipped `verify_receipt.py` reports
  `signature: FAIL → RESULT: NOT VERIFIED` on a **genuine** receipt — indistinguishable, to a journal
  editor, from a forgery. It now refuses with **HTTP 409** rather than emit a key that cannot verify
  the signature next to it.

Still open: only one key is held at a time, so rotation makes old receipts un-exportable (they 409
loudly instead of lying). A **keyring** — verify against any known kid, sign with the newest — is the
real fix.

### Still open

- **`JWT_SECRET` is dead config**: compose fail-closed *requires* it, `.env.example` defines it, and
  **no backend code reads it**. `auth_service` reads `JWT_SECRET_KEY`.
- If `DATABASE_URL` is unset the backend **silently falls back to SQLite**. Compose sets it, so the
  compose path is safe — but any bare `manage.py` invocation writes to `db.sqlite3`.
- If Redis is unreachable at import time, settings **silently falls back to LocMemCache** (per
  gunicorn worker) with only a stdout warning.
- `nginx/ssl/` and `nginx/sites-enabled/` are mounted by compose but **do not exist in the repo** —
  TLS material must already be on the host.

## 5. Beta access — SETTLED (2026-07-14): it WAS rotated

**Single source of truth: `/root/stickforstats-beta-access.txt` on the host.** Username `beta`;
bcrypt hash in `nginx/ssl/.htpasswd`. The secret is **deliberately not written into this repo** and
must not be.

Verified properly rather than inferred: the credential in that file passes `htpasswd -vb` against the
live `.htpasswd`, and authenticates through the edge (HTTP 200). The host file and the nginx
container's mounted copy have identical md5, so there is no stale-mount ambiguity.

`SESSION_HANDOFF_2026-07-13-POWER.md`'s "**NOT** rotated" bullet is **stale and wrong**. It was
repeated for two days because no document said which document to trust — which is exactly why
`docs/README.md` is now an undated index.

> **Method note, worth keeping:** a `401` for an old password proves *nothing* — the edge returns 401
> for any credential, including one that never existed. Only `htpasswd -v` against the live file, or a
> successful `200`, settles it. This is the same discipline as the rest of this project: **an absence
> of evidence is not evidence, and a plausible inference is not a verification.**

⚠ At least one **stale** password string is in circulation outside the host; it fails `htpasswd -v`
against the live file. Check any written-down beta password against the host before using it.
